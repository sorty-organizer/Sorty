## Review and evidence

The baseline-to-candidate inventory spans 482 files. This preparation inspected
commit history, existing incident notes, release surfaces, preview regeneration,
Expiring Files review/trash handling, duplicate restoration, and the latest failed
Swift CI logs. It is not an exhaustive line-by-line review of every changed file
and does not establish that the release is bug free.

A pre-trash Expiring Files check reused the URL returned by directory enumeration,
which prefetches resource values. It now reconstructs the URL before checking
metadata, avoiding the scan's cached values. A standalone Foundation experiment reproduced the cache issue: after a file
grew from 1 to 3 bytes, the enumerated URL still reported 1 while a fresh URL
reported 3. This verifies the cache mechanism, not the complete Trash UI.
The existing check compares arrival
date and size; it does not establish content identity or detect every same-size
edit. No broader file-identity guarantee is claimed.

Swift CI run 41219089356 failed
`DuplicateRestorationManagerTests.testRestoreDoesNotDependOnSurvivingDuplicate`
with `trashedFileNotFound`. Earlier occurrences and unchanged-source successes
are documented in `docs/agent-guides/code-reduction.md`. The underlying cause
remains unproven; this preparation does not weaken that test or substitute a
mock for macOS Trash.

Production analysis hangs 4R and 4S were reported on the old 1.3.0 build.
See `docs/agent-guides/sentry-triage-2026-11-03.md`; removal of the rotating
message timer and isolation of the cancellation dialog still need evidence
from a distributed candidate. Do not mark those incidents resolved yet.

## Learnings incident 4V

Retrieved Sentry event `7455f044bdb0485080cad34c7d9d28ab` for
SORTY-MACOS-4V. It is a handled load_profile error on internal development
build 1.3.0+2920. The event retains only UnclassifiedError, without an underlying
exception or stack. Local logs at the event time show Keychain activity but
no specific failure; they do not establish the cause. The current local profile
exists and was modified after the event; no profile data or credentials were read
or changed during this investigation.

LearningsFileError was absent from ReliabilityManager's typed classification.
Added fixed categories for unavailable keys, Keychain save/delete failures,
encryption/decryption failures, and quarantined profiles. No error payloads,
profile contents, or paths are sent. This fixes diagnostic ambiguity for future
events, not the unproven cause of this event. Keep 4V open pending useful
classification or a reproduction. Existing profile-load failure handling leaves
the in-memory profile nil to avoid overwriting stored data with an empty profile.
